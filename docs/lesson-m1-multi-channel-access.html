1. 设计背景：为什么需要多渠道统一入口

DeerFlow 的核心是一个 Agent Runtime，但不同用户有不同的使用场景：

接入方式典型用户是否依赖 HTTP 服务
Web 浏览器终端用户是（Nginx :2026）
LangGraph SDK开发者 / 第三方集成是（Nginx :2026 → /api/langgraph/*）
DeerFlowClient 内嵌Python 脚本 / 库集成否（进程内直接调用）
TUI 终端命令行用户 / 运维否（基于 DeerFlowClient）
核心设计原则：所有接入方式最终都汇聚到同一个 Agent 执行路径 make_lead_agent() → assemble_lead_agent() → run_agent()， 不在接入层复制 Agent 逻辑。TUI 和 DeerFlowClient 是UI shell / 编程壳，不 fork agent 行为。

3. Nginx 路由契约（真实配置）

Nginx 是唯一对外暴露的入口（端口 2026），Gateway 的 8001 端口不对外发布。关键路由规则来自 docker/nginx/nginx.conf：

路径目标说明
/api/langgraph/*Gateway :8001重写为 /api/* 再转发（LangGraph 兼容层）
/api/*（其它）Gateway :8001Gateway REST 路由直接转发
/api/sandboxesProvisioner :8002沙箱管理（K8s/provisioner 模式）
/healthGateway :8001健康检查
/*Frontend :3000Next.js 静态与页面

LangGraph 兼容层的重写规则

# docker/nginx/nginx.conf
location /api/langgraph/ {
    rewrite ^/api/langgraph/(.*) /api/$1 break;  # 去掉 langgraph 前缀
    proxy_pass http://gateway:8001;
    proxy_set_header Connection '';              # SSE 流式支持
    proxy_set_header X-Accel-Buffering no;
    client_max_body_size 20M;                    # 长 prompt 支持
    proxy_request_buffering off;
    proxy_read_timeout 600s;                     # 长对话超时
}
为什么需要重写？LangGraph SDK 客户端默认请求 /api/langgraph/*， 而 Gateway 的路由是 /api/*。Nginx 在转发前去掉 langgraph 前缀， 让同一套 Gateway 路由同时服务 Web UI 和 LangGraph SDK。

4. Gateway Runtime 启动：langgraph_runtime lifespan

Gateway 在 FastAPI lifespan 中通过 langgraph_runtime() 一次性初始化所有运行时单例。这些单例是重启生效的（持有连接/文件句柄），不随 config.yaml 热更新。

启动顺序（来自 app/gateway/deps.py）

  1. 多 worker 安全门：GATEWAY_WORKERS > 1 时拒绝 SQLite（写锁不支持多进程）
  2. freeze_checkpoint_channel_mode() — 冻结 checkpoint 模式（full/delta）
  3. make_stream_bridge() — SSE 流桥（memory / redis）
  4. init_engine_from_config() — 初始化持久化引擎（先于 checkpointer，确保 PG 自动建库）
  5. make_checkpointer() — LangGraph checkpointer（memory/sqlite/postgres）
  6. make_store() — LangGraph Store
  7. 初始化仓库：RunRepository、FeedbackRepository 等
# app/gateway/deps.py::langgraph_runtime (简化)
async with AsyncExitStack() as stack:
    app.state.checkpoint_channel_mode = freeze_checkpoint_channel_mode(...)
    app.state.stream_bridge = await stack.enter_async_context(make_stream_bridge(config))
    await init_engine_from_config(config.database)
    app.state.checkpointer = await stack.enter_async_context(make_checkpointer(config))
    app.state.store = await stack.enter_async_context(make_store(config))
    # ... 仓库初始化
重启边界：database、checkpointer、stream_bridge、sandbox 等字段属于 STARTUP_ONLY_FIELDS，运行时修改 config.yaml 不会生效，必须重启 Gateway。 而 models、tools、summarization 等字段每次请求通过 get_app_config() 热加载。

6. DeerFlowClient：进程内嵌客户端（不走 HTTP）

DeerFlowClient 提供不依赖 Gateway 服务的编程接入方式，直接导入 harness 的 agent 组装逻辑。适合 Python 脚本、库集成、测试。

核心 API

方法签名返回
chat()chat(message, *, thread_id=None, **kwargs) -> str最后一条 AI 消息的累积文本
stream()stream(message, *, thread_id=None, **kwargs) -> Generator[StreamEvent]流式事件（values / messages-tuple / custom / end）
list_models()—模型列表（与 Gateway /api/models 对齐）
list_skills()—技能列表
get_mcp_config() / update_mcp_config()—MCP 配置读写
upload_files()—文件上传（接收 Path 对象，非 HTTP UploadFile）

chat() 实现原理

chat() 是 stream() 的便利封装：按消息 id 累积 messages-tuple 的 delta，最后返回最后一条 AI 消息的拼接文本。

# deerflow/client.py::chat (简化)
def chat(self, message, *, thread_id=None, **kwargs) -> str:
    chunks: dict[str, list[str]] = {}
    last_id = ""
    for event in self.stream(message, thread_id=thread_id, **kwargs):
        if event.type == "messages-tuple" and event.data.get("type") == "ai":
            msg_id = event.data.get("id") or ""
            delta = event.data.get("content", "")
            if delta:
                chunks.setdefault(msg_id, []).append(delta)
                last_id = msg_id
    return "".join(chunks.get(last_id, ()))
多轮对话需要 checkpointer：不传 checkpointer 时每次调用是无状态的， thread_id 仅用于文件隔离（uploads / artifacts）。要实现多轮上下文，需传入 checkpointer 实例。

7. TUI 终端：基于 DeerFlowClient 的终端 UI

TUI（deerflow 控制台脚本）是 DeerFlowClient 之上的终端 UI 壳，不 fork agent 行为。核心分层（全部除 app.py 外均为纯函数，可单测）：

模块职责
cli.py启动模式决策（TTY→TUI，非 TTY→headless help）、--print/--json
session.py构建 DeerFlowClient + checkpointer，线程解析（--resume/--continue）
runtime.pytranslate(StreamEvent) → [Action] 纯函数 + stream_actions() 驱动
view_state.pyViewState + reduce(state, action)，可测核心
app.pyTextual App，worker 线程跑 client.stream()，UI 线程 apply action
persistence.py写 threads_meta 表，让 TUI 会话出现在 Web UI

关键设计：TUI 会话如何出现在 Web UI

Web UI 的侧边栏线程列表来自 threads_meta SQL 表（用户域），而非 checkpointer。TUI 的 persistence.py 通过 init_engine_from_config() 在默认用户（"default"）下写入 threads_meta 行，使用与 Gateway 相同的数据库——因此 TUI 创建的会话无需启动 Gateway 也能在 Web UI 看到。

无 SQL 后端时降级：当 database.backend 为 memory 时，threads_meta 写入是 no-op， TUI 会话不会出现在 Web UI。

9. 实践作业

  1. 对比 HTTP 与内嵌调用：用 DeerFlowClient 在 Python 脚本中发起一次对话（不传 checkpointer），再用 curl 调用 http://localhost:2026/api/threads/{id}/runs/wait，对比两者的输出结构是否一致。
  2. 验证 Nginx 重写：用 curl -v http://localhost:2026/api/langgraph/threads，确认请求到达 Gateway 时路径为 /api/threads（查看 Gateway 日志或抓包）。
  3. TUI 会话可见性：用 TUI 创建一个会话，然后打开 Web UI，确认该会话出现在侧边栏（需 database.backend: sqlite 或 postgres）。
  4. 无 checkpointer 的无状态验证：用 DeerFlowClient（不传 checkpointer）连续发两条消息，验证第二条无法记住第一条的上下文。

10. 小结与思考题

小结：DeerFlow 通过「HTTP 路径（Web/SDK）+ 进程内路径（Client/TUI）」两条路径复用同一 Agent Runtime。Nginx 用路径重写实现 LangGraph SDK 兼容；Gateway lifespan 一次性初始化运行时单例；DeerFlowClient 提供与 Gateway API 对齐的编程接口；TUI 在 Client 之上加终端 UI 并通过 threads_meta 实现跨端可见。

思考题

  1. 为什么 Gateway 的 8001 端口不对外发布，只暴露 Nginx 的 2026？
  2. DeerFlowClient 的 chat() 为什么按 id 累积 delta 而不是直接拼接字符串？（提示：长响应的 O(n²) 问题）
  3. 如果要新增一种接入方式（例如 gRPC），应该在哪一层扩展，才能不复制 Agent 逻辑？
